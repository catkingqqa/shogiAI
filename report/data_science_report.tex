\begin{abstract}
本報告說明 shogiAI 專案中的數據科學部分。專案以 1000 份日本將棋 CSA 棋譜為資料來源，先經由 \texttt{cshogi} 解析與合法性檢查，再將棋局匯入 MySQL，最後從資料庫匯出可訓練的 policy/value dataset。模型任務包含兩個目標：第一，根據目前局面預測人類棋手的下一手；第二，根據目前下棋方視角估計該局面最後勝負。本專案使用 $43 \times 9 \times 9$ 的局面張量、13689 類走法標籤、小型 CNN policy/value network、AdamW 最佳化器、CosineAnnealingLR 學習率排程，並將模型推論結果整合到 alpha-beta 搜尋，用於 AI 對弈與候選手展示。報告重點包含資料來源、特徵工程、標籤設計、模型架構、訓練方法、評估指標、搜尋整合、限制與改進方向。
\end{abstract}

\section{專案在數據科學中的定位}

shogiAI 的數據科學目標不是單純訓練一個分類器，而是建立一條完整的棋類 AI 資料流程：

\[
\text{原始棋譜}
\rightarrow
\text{合法局面資料}
\rightarrow
\text{監督式學習樣本}
\rightarrow
\text{Policy/Value 模型}
\rightarrow
\text{搜尋系統輔助}
\]

在棋類 AI 中，資料科學扮演三個角色：

\begin{enumerate}
  \item \textbf{資料表示：} 將人類棋譜中的文字格式轉換為可計算的張量。
  \item \textbf{模式學習：} 從歷史棋譜中學習人類在不同局面下的走法偏好與勝負趨勢。
  \item \textbf{決策輔助：} 將模型輸出用於排序合法手、估計局面價值，輔助傳統搜尋演算法。
\end{enumerate}

因此本專案結合了資料工程、監督式學習、深度學習與傳統搜尋。資料科學部分的核心問題可表述為：

\[
f_\theta(s) = (p, v)
\]

其中 $s$ 是目前將棋局面，$p$ 是對所有可能走法的 policy 分數，$v$ 是目前下棋方的勝負價值估計。

  \item 棋手名稱與先後手。
  \item 賽事、日期、場地、開局等 metadata。
  \item 初始盤面。
  \item 每一手走法。
  \item 終局結果，例如投了、千日手、和棋。
\end{itemize}

\subsection{資料處理管線}

專案的數據處理流程如下：

\begin{enumerate}
  \item 使用 \texttt{src/import\_csa\_to\_db.py} 解析 CSA 棋譜。
  \item 使用 \texttt{cshogi.CSA.Parser} 取得棋局、走法與勝負結果。
  \item 使用 \texttt{cshogi.Board} 從初始局面逐手重播。
  \item 對每一手使用 \texttt{board.is\_legal(move)} 檢查合法性。
  \item 將棋局、棋手、走法與每手局面寫入 MySQL。
  \item 使用 \texttt{src/export\_policy\_dataset.py} 從資料庫匯出模型資料。
  \item 將每筆資料轉為 $(state, move, value)$ 形式。
  \item 使用 \texttt{numpy.savez\_compressed} 儲存成 \texttt{out/policy\_dataset.npz}。
\end{enumerate}

這個流程的關鍵是「訓練資料從資料庫匯出，而不是直接從原始檔案訓練」。這樣可確保資料已經經過一致的解析、清洗、合法性檢查與 metadata 整理，也方便日後用 SQL 篩選特定賽事、棋手或日期區間。

\section{問題定義}

\subsection{Policy Learning}

Policy learning 的任務是：給定目前局面 $s_t$，預測實戰中的下一手 $a_t$。

\[
P_\theta(a_t \mid s_t)
\]

這是一個多類別分類問題。每一筆訓練資料包含：

\[
(s_t, a_t)
\]

其中 $s_t$ 是局面張量，$a_t$ 是實戰走法的整數標籤。

\subsection{Value Learning}

Value learning 的任務是：給定目前局面 $s_t$，預測目前下棋方最後是否會獲勝。

\[
V_\theta(s_t) \in [-1, 1]
\]

標籤定義為：

\[
z_t =
\begin{cases}
1, & \text{目前下棋方最後獲勝}\\
0, & \text{和棋或千日手}\\
-1, & \text{目前下棋方最後落敗}
\end{cases}
\]

這種定義比直接預測「黑方勝率」更適合 negamax 搜尋，因為搜尋演算法本身也是從目前手番視角評分。

\section{特徵工程：局面編碼}

\subsection{為什麼需要特徵工程}

CSA、USI、SFEN 都是文字格式，神經網路無法直接使用。模型需要固定形狀的數值張量。本專案將每個局面編碼成：

\[
state \in \mathbb{R}^{43 \times 9 \times 9}
\]

其中 9x9 對應將棋棋盤，43 個 channel 對應不同棋子、持駒與手番資訊。

\subsection{棋盤棋子平面}

將棋棋子類型包含未升變與升變後棋子。本專案使用 14 種棋子類型：

\begin{itemize}
  \item 步、香、桂、銀、金、角、飛、王。
  \item 成步、成香、成桂、成銀、馬、龍。
\end{itemize}

棋盤上的棋子分為己方與對方，因此：

\[
14 \times 2 = 28
\]

前 28 個平面用於表示棋盤上每格是否有某一類棋子。

\subsection{持駒平面}

將棋和西洋棋最大的不同之一是「持駒打入」。吃掉對手棋子後，棋子會變成自己的持駒，可在之後打回棋盤。因此局面表示必須包含持駒數量。

可打入的持駒類型有 7 種：

\[
\{\text{步, 香, 桂, 銀, 金, 角, 飛}\}
\]

本專案使用：

\begin{itemize}
  \item 7 個平面表示己方持駒數量。
  \item 7 個平面表示對方持駒數量。
\end{itemize}

持駒平面不是 one-hot，而是整個 $9 \times 9$ 平面填入該棋子持有數量。這讓 CNN 在任何位置都能讀到持駒資訊。

\subsection{手番平面}

第 43 個平面用於補充輪到誰下或視角資訊。棋類模型必須知道手番，因為同一個盤面輪到不同方下，局面價值與合法手完全不同。

\subsection{視角旋轉}

專案預設使用 \texttt{orient\_to\_turn=True}。當輪到白方時，棋盤會旋轉 180 度，使模型總是從目前下棋方的角度觀察局面。

優點：

\begin{itemize}
  \item 降低黑白方向差異。
  \item 增加資料對稱性。
  \item 讓相似攻防型態在模型眼中具有相同方向。
\end{itemize}

例如黑方的「向前推步」與白方的「向前推步」，若不旋轉，對模型而言方向相反；旋轉後都成為同一種局部模式。

\section{標籤設計：走法編碼}

\subsection{一般移動}

一般移動由三個資訊組成：

\begin{itemize}
  \item 來源格：81 種。
  \item 目標格：81 種。
  \item 是否升變：2 種。
\end{itemize}

因此一般移動標籤數為：

\[
81 \times 81 \times 2 = 13122
\]

\subsection{持駒打入}

打入走法不需要來源格，而是由：

\begin{itemize}
  \item 打入棋子種類：7 種。
  \item 目標格：81 種。
\end{itemize}

因此打入標籤數為：

\[
7 \times 81 = 567
\]

\subsection{總走法空間}

總 policy 類別數：

\[
13122 + 567 = 13689
\]

雖然任一局面中合法手通常遠少於 13689，但固定輸出空間使模型可以使用標準 cross entropy 訓練。

\section{模型架構}

\subsection{整體架構}

模型定義於 \texttt{src/policy\_model.py}，名稱為 \texttt{SmallPolicyValueNet}。其結構如下：

\[
x \in \mathbb{R}^{43 \times 9 \times 9}
\]

\[
h = f_{\text{conv}}(x)
\]

\[
\hat{p} = f_{\text{policy}}(h), \quad \hat{p} \in \mathbb{R}^{13689}
\]

\[
\hat{v} = f_{\text{value}}(h), \quad \hat{v} \in [-1,1]
\]

\subsection{Feature Extractor}

Feature extractor 使用三層卷積：

\begin{lstlisting}[style=cmd]
Conv2d(43, 64, kernel_size=3, padding=1)
ReLU
Conv2d(64, 64, kernel_size=3, padding=1)
ReLU
Conv2d(64, 32, kernel_size=3, padding=1)
ReLU
\end{lstlisting}

卷積適合棋盤任務，因為棋子攻防、王周圍安全、升變區、棋子保護都和局部空間結構有關。

\subsection{Policy Head}

Policy head 將卷積特徵展平後輸出 13689 類：

\begin{lstlisting}[style=cmd]
Flatten
Linear(32 * 9 * 9, 512)
ReLU
Linear(512, 13689)
\end{lstlisting}

輸出是 logits，不直接經過 softmax。訓練時由 \texttt{CrossEntropyLoss} 內部處理 softmax；推論時只取合法手對應的 logits。

\subsection{Value Head}

Value head 輸出單一數值：

\begin{lstlisting}[style=cmd]
Flatten
Linear(32 * 9 * 9, 128)
ReLU
Linear(128, 1)
Tanh
\end{lstlisting}

最後使用 \texttt{Tanh}，使輸出範圍落在 $[-1,1]$，符合勝負標籤定義。

\section{訓練方法}

\subsection{資料切分}

資料切分由 \texttt{split\_by\_game} 完成，以棋局為單位切分：

\begin{itemize}
  \item 訓練集：約 80\% 棋局。
  \item 驗證集：約 10\% 棋局。
  \item 測試集：約 10\% 棋局。
\end{itemize}

目前 checkpoint 中記錄：

\begin{longtable}{p{0.42\textwidth}p{0.42\textwidth}}
\toprule
\textbf{集合} & \textbf{樣本數}\\
\midrule
\endhead
Train & 88473\\
Validation & 11166\\
Test & 11599\\
\bottomrule
\end{longtable}

以棋局為單位切分是為了避免資料洩漏。若隨機切分每一筆樣本，同一盤棋的相鄰局面可能同時出現在訓練與測試中，使測試分數不真實。

\subsection{損失函數}

總損失：

\[
\mathcal{L} =
\mathcal{L}_{policy}
+ \lambda \mathcal{L}_{value}
\]

其中 policy loss 使用 cross entropy：

\[
\mathcal{L}_{policy}
=
-\log
\frac{\exp(\hat{p}_{a})}
{\sum_j \exp(\hat{p}_j)}
\]

value loss 使用 MSE：

\[
\mathcal{L}_{value}
=
m(\hat{v} - z)^2
\]

$m$ 是 value mask，$z$ 是勝負標籤，$\lambda$ 對應 \texttt{value-loss-weight}，目前使用 0.25。

\subsection{最佳化器與學習率}

訓練使用：

\begin{itemize}
  \item Optimizer：AdamW。
  \item Learning rate：$10^{-3}$。
  \item Weight decay：$10^{-4}$。
  \item Scheduler：CosineAnnealingLR。
  \item Epochs：12。
\end{itemize}

AdamW 比一般 Adam 更適合搭配 weight decay，可減少過度擬合。Cosine annealing 會使學習率逐步下降，讓訓練後期更新更穩定。

\section{評估指標}

\subsection{Policy 指標}

Policy 使用 Top-k accuracy：

\begin{itemize}
  \item Top-1：模型最高分走法是否等於實戰走法。
  \item Top-3：實戰走法是否在模型前三名。
  \item Top-5：實戰走法是否在模型前五名。
\end{itemize}

棋類任務中 Top-5 很有意義，因為一個局面可能有多個合理手。模型不一定要完全猜中人類實戰手，只要能把合理候選手排在前面，就能輔助搜尋。

\subsection{Value 指標}

Value 使用：

\begin{itemize}
  \item MSE loss。
  \item MAE。
\end{itemize}

MAE 可解釋為模型平均預測值與真實勝負標籤之間的距離。

目前測試集結果：

\section{模型推論與搜尋整合}

\subsection{推論流程}

推論由 \texttt{PolicyValuePredictor} 處理：

\begin{enumerate}
  \item 載入 \texttt{out/policy\_model.pt}。
  \item 讀取 checkpoint 中的 \texttt{move\_label\_count} 與 \texttt{orient\_to\_turn}。
  \item 將 \texttt{cshogi.Board} 編碼成 state tensor。
  \item 呼叫 PyTorch model 得到 logits 與 value。
  \item 使用 zobrist hash 快取相同局面的推論結果。
\end{enumerate}

\subsection{合法手排序}

模型輸出 13689 類，但實際下棋只能選合法手。推論時：

\[
\text{score}(a) = \hat{p}_{label(a)}
\quad
\text{for } a \in A(s)
\]

其中 $A(s)$ 是目前局面的合法手集合。接著只對合法手 logits 做 softmax，得到前端顯示的候選手機率。

\subsection{與 Alpha-Beta 搜尋整合}

AI 對弈不是直接選 policy 最大手，而是把 policy 用於 move ordering：

\[
\text{legal moves}
\rightarrow
\text{policy rank}
\rightarrow
\text{alpha-beta search}
\]

Alpha-beta 搜尋越早看到好手，越容易剪掉後續分支。因此 policy model 的主要作用是提升搜尋效率與候選手品質，而不是完全取代搜尋。

Value head 可作為根節點加權評估：

\[
\text{score} =
\text{handcrafted evaluation}
+ w \cdot V_\theta(s)
\]

其中 $w$ 由 \texttt{--value-weight} 控制。

\section{數據科學上的限制}

\begin{enumerate}
  \item \textbf{資料量有限：} 1000 盤棋可完成原型，但對強棋力深度模型而言仍偏少。
  \item \textbf{Value label 較粗糙：} 只由終局勝負回推，沒有中盤局面引擎分數。
  \item \textbf{模型架構較小：} 尚未使用 residual blocks、attention 或 transformer。
  \item \textbf{未在訓練時使用合法手 mask：} 目前 loss 對 13689 類完整空間計算，未直接限制非法手。
  \item \textbf{資料分布不平衡：} 大部分結果為投了，和棋樣本很少。
\end{enumerate}

\section{改進方向}

\begin{itemize}
  \item 增加棋譜數量，包含職業棋譜、公開對局與自我對弈資料。
  \item 加入合法手 mask loss，使模型更專注於合法候選手。
  \item 使用 residual CNN 或 transformer 架構提升棋型表達能力。
  \item 使用強引擎為中盤局面產生 centipawn-like 評分，改善 value head。
  \item 針對不同手數階段建立 opening/middlegame/endgame 分析。
  \item 將 policy model 與搜尋結果記錄回資料庫，形成模型評估資料表。
\end{itemize}

\section{結論}

shogiAI 的數據科學部分展示了從原始棋譜到可互動 AI 的完整建模流程。專案並非只訓練模型，而是先建立資料庫與資料清洗流程，再設計局面張量、走法標籤、勝負標籤，最後用 CNN 學習 policy/value，並整合到 alpha-beta 搜尋。這種架構兼具資料可追蹤性、模型可訓練性與系統可展示性，是資料科學與傳統 AI 結合的完整範例。
